Guide, arrow rails and tab widths

The guide reveals the actual control.

A closed native section can report a nonzero bounding box for hidden descendants. The guide now opens only the necessary presentation sections, centers the real target clear of the dock, and keeps the scrollable guide panel above or below it before drawing its ring. Hidden or removed targets lose the ring. It does not click actions or reveal conditional workflow fields.

Full-height arrow rails on shared cards.

The role-card stylesheet loaded after the mobile styles and reset the grid and padding. That squeezed the arrow into a narrow inset strip in Customers and Recent sales. The shared card rules now have sufficient specificity, shared cards/Sales orders use the same 52-pixel rail token, and customer lists use the shared 12-pixel card gap.

One canvas across the five tabs.

Home, Work and Clock used a narrower cap, while Profile added another horizontal inset. The tab overviews now share the mobile shell’s 560-pixel maximum canvas and its normal gutters. The floating dock retains its stable width; record forms and active conversation layouts keep their task-specific structure.

Review brief and method
  1. Professional check: distinguish geometric boxes from painted controls, inspect the full CSS cascade, and measure content edges rather than assume identical widths from screenshots.
  2. Raw material: guide target resolution and native details state, actual shared RoleUI markup, stylesheet order/computed grid/padding, all five tab containers and fresh customer/order API records.
  3. Methods/tools: installed Taste app-screen guidance for aligned canvas edges; UI UX Pro Max’s focus-not-obscured guidance; Playwright visibility, rail geometry, narrow/tablet/desktop measurements, screenshots and regression traces; shared guide runtime tests. Use native disclosure state instead of clicking business controls. Preserve existing motion and verify reduced motion. Sites publishes this actual-code private preview.
  4. Independent evidence: the previous app fails the closed-section guide, full-height rail and tab-width assertions. Passing requires a visible target inside the guide ring, no ring on hidden/removed targets, flush rails in both themes, identical tab content bounds at all tested widths, and unchanged navigation/action safeguards.

Brief: Fix the four reported mobile defects in the existing design: reveal a guide target’s closed presentation sections before highlighting, repair shared arrow rails in Customers and Recent sales, and make primary-tab canvas widths consistent. Verification and remaining limits

Playwright results will be written here after verification.

Browser interactions and animations run real app code. The managed test browser blocks file:// navigation, so verification serves this same standalone HTML on loopback. Opening the file directly in other browsers is not yet verified. Records were captured from a disposable backend at build time; this file replays them offline. Business writes, uploads and uncaptured destinations are explicitly blocked. Only notification read markers and shortcut preferences may update isolated sample memory. Test records, history and forms never reach the live app.

Notification read markers, saved shortcut choices and browser storage use memory only. This does not test persistence across restart, camera/GPS, printers, a physical phone, a real screen-reader session, or first-time employee understanding. Shared code applies across mobile, but the browser checks cover the named representative screens and controls rather than every legacy screen. An exploratory full-page 200% CSS zoom inside an already 320-pixel phone frame reduced its effective layout to about 160 pixels and exposed overlap in the existing global header/dock. That app-wide shell limitation remains not covered by this normal-zoom guide/layout check; the tested 320/390-pixel layouts below use normal page zoom.
