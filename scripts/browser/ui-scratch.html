Tab-switch loading correction

Unchecked queues stay compact.

The flash came from mounting every authorized Work queue with a loading heading and a View queue link, then removing empty queues after the reads finished. On the empty fixture, content briefly grew from about 296 to 1,275 pixels. Now one Checking current work status represents unchecked queues. Actual pending work and failed checks appear as their results arrive.

Home sections respond to the first tap.

The shared disclosure helper kept its initial closed state even when a queue read had opened the section. The first tap could try to open it again. It now reads the current open state when idle and still handles interrupted close/reopen animation correctly.

Known records remain visible during refresh. Errors stay unknown, pending work still opens on Home, and the compact tools directory starts closed. No page entrance animation, artificial delay, blanket hiding of work, or workflow change was added.

Try it

  1. Start with Warehouse · checked empty. Switch repeatedly between Home and Work using the phone’s bottom dock. Work should not briefly expand a long list of unchecked queues.
  2. Set Queue checks to Delayed. Switch tabs while reads are in flight, then return to Work. A compact loading status should stay visible until actual results arrive.
  3. Choose Warehouse with kits, QC, QA and RTS. Home’s pending categories still open automatically. Tap a category once to close it, then again to open it.
  4. Set checks to Unavailable. Failed queues must show their unknown/error state instead of disappearing or claiming no work.

Verification and remaining limits

Playwright results will be written here after verification.

Browser interactions and animations run real app code. The managed test browser blocks file:// navigation, so verification serves this same standalone HTML on loopback. Opening the file directly in other browsers is not yet verified. Records were captured from a disposable backend at build time; this file replays them offline. Business writes, uploads and uncaptured destinations are explicitly blocked. Only notification read markers and shortcut preferences may update isolated sample memory. Test records, history and forms never reach the live app.

Notification read markers, saved shortcut choices and browser storage use memory only. This does not test persistence across restart, camera/GPS, printers, a physical phone, a real screen-reader session, or first-time employee understanding. Shared code applies across mobile, but the browser checks cover the named representative screens and controls rather than every legacy screen. An exploratory full-page 200% CSS zoom inside an already 320-pixel phone frame reduced its effective layout to about 160 pixels and exposed overlap in the existing global header/dock. That app-wide shell limitation remains outside this Sales-list refinement; the tested 320/390-pixel layouts below use normal page zoom.
