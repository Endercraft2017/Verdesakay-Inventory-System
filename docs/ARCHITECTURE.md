## 1. Overview

A LAN office system: **inventory**, **forms/files**, **user accounts with roles &
departments**, and **internal messaging**. One PC runs the server; other PCs use it in a
browser.

**Roles & permissions:** 8 roles (`admin`, `admin_staff`, `accounting`, `warehouse`,
`releasing`, `csr`, `hr`, `marketing`) each with granular per-feature permission defaults
defined in `src/permissions.ts`. Admins can override permissions per-individual via the
Accounts UI. Resolved effective permissions are a `Permission[]` on every `AuthUser`.
`forms.manage` (create/edit/delete form definitions + global variables) is admin-only by default.

- **Backend:** Node.js + Express + TypeScript (run with `tsx`, no build step).
- **Database:** SQLite via Node's built-in `node:sqlite` (file: `data.db`).
- **Frontend:** vanilla HTML/CSS/JavaScript SPA in `public/` (no framework, no build step for the
  app itself). One exception: `public/js/vendor/codemirror-bundle.js` — a pre-built CodeMirror 6
  bundle, the project's only external frontend dependency, vendored (not loaded from a CDN, since
  this is a LAN app that may run with no internet access) — see its row in §2 for what it is and
  how to rebuild it.
- **Auth:** bearer session tokens in the `sessions` table (12 h expiry); bcrypt passwords.
- **Validation:** `zod` schemas (`src/validation.ts`). **Security:** `helmet` + login
  rate-limiting. **Tests:** `vitest` + `supertest` (`tests/`).

### Request flow
```
Browser (public/js/*) --fetch--> Express (src/app.ts)
  -> helmet, json/urlencoded, login rate-limit, request log + activity log (mutations)
  -> route (src/routes/*.ts): requireAuth -> requirePermission(key)? -> parseBody(zod)
  -> DB helpers (queryOne/queryAll/run in src/db.ts) -> node:sqlite
  -> JSON response  |  errors -> central handler in app.ts
```

| `src/routes/form-builder.routes.ts` | `/api/form-definitions`, `/api/form-records`, `/api/global-variables` — per-section-managed custom form types (with JSON field defs + a `scope`: `'hr'\|'inventory'\|'admin'\|'accounting'\|null`), per-form record CRUD (auto-numbered), and global template variables. **Authorization is scope-aware, not a static `requirePermission(...)`**: a form's required permission (`forms.manage.<scope>`) depends on the row's own `scope`, known only after looking it up (or, for create, from the request body) — so `canManageScope(req, res, scope)` is called inline inside each handler instead. Moving a form to a different scope (`PUT /form-definitions/:id`) requires permission for *both* the old and new scope. `scope: null` ("General", an unowned bucket) requires *all four* `forms.manage.*` — stricter than any single section, effectively admin-only by default. `PUT/DELETE /global-variables/:key` use `requireAnyPermission` across all four instead (globals are shared across every section, not owned by one). `PUT /form-definitions/:id/template` (link an *existing* `doc_template` by id) follows the same current-scope check. **`PUT /form-definitions/:id/template-body`** goes further — it creates (first use, `INSERT INTO doc_templates` + auto-links) or updates (upsert) a `doc_template`'s actual *content* directly, authorized the same scope-aware way instead of the broader `templates.edit` (which stays reserved for `/api/templates` in `templates.routes.ts` — the hand-authored Sale/Job/Purchase Order etc. templates unrelated to any one form). This is what lets e.g. an `hr`-role user design their own forms' printable look without needing `templates.edit` at all. Also `POST /form-definitions/:id/import` — bulk-create records from the payroll "Summary" CSV (multer memory storage; optional `pay_date` body field stamped onto every row); 400s unless the target form's slug is `hr_payroll` (still `hr.manage`-gated, unrelated to the scope system). |
| `src/hr-payroll-compute.ts` | `computeAttendanceForEmployee(days, dailyRate, policy)` — pure computation (no DB access, same separation-of-concerns as `hr-payroll-import.ts` below) turning one employee's attendance days + whatever HR forms are linked to each + the company `PayrollPolicy` into `{days_worked, late_deduction, ot_hours, overtime_pay, undertime_pay, holiday_pay, special_holiday_30}`. Per day: no time logged + a linked `leave_request` form with `data.with_pay === 'Yes'` → a full paid day; a `halfday_request` link → 0.5 day credit; late arrival is judged against the day's resolved shift start, **grace is a threshold not a subtracted buffer** (once exceeded, only the minutes *past* grace round up to the policy's block size — confirmed precisely: 125 min late, 10 min grace, 1-hour block → 115 min past grace → 2 hours deducted, not 3); OT is only credited when a `overtime_request` form is linked (a raw late clock-out alone never becomes paid OT) and rounds up the same way; an `offset_form` link shifts that day's *expected time-out* (`data.new_time_out`) before the OT/undertime checks; `holiday_work_request` adds the PH premium-on-top convention (100% for Regular Holiday into `holiday_pay`, 30% for Special Non-Working into `special_holiday_30` — the field name literally encodes the rate). **A company-wide "No Work Memo"** (`AttendanceDay.noWork: 'paid'|'unpaid'|null`, `slug: 'no_work_memo'`, fields `date_from`/`date_to`/`reason`/`paid`) is a *different* mechanism from every other linked form above — it's not linked to any one attendance row at all. `src/routes/hr.routes.ts` resolves it once per `generate-payslips` call (fetches every `no_work_memo` record, keeps a `workDate >= date_from && workDate <= date_to` matcher) and applies it to *every* employee's matching day automatically — a `paid` memo credits a full day exactly like a paid Leave form (Leave still takes precedence if both apply), an `unpaid` one is numerically identical to a plain absence but is carried through as a distinct value for anyone extending this later, and it never overrides a day where real time was actually logged (it only ever excuses an *absence*). **Overnight shifts** (end time numerically before start time, e.g. 22:00→06:00) are handled by normalizing every clock reading onto a single continuous timeline anchored at shift start (`relTo()`) before any comparison — this was a real bug caught by its own test suite (naively subtracting raw "HH:MM" minutes across a midnight wrap produced nonsense like 17 hours of "overtime"); night-differential overlap (optional, config in `PayrollPolicy`) handles the same wrap by checking both the window's "today" and "tomorrow" instance. Pure, no I/O — unit tested directly (`tests/hr-payroll-compute.test.ts`), including the overnight-wrap and rotating-shift (different shift per day) cases. |
| `src/hr-payroll-import.ts` | `parseCsvRows()` (small RFC4180-ish CSV tokenizer) + `parsePayrollSummaryCsv()` — extracts `PayrollSlip` records from the payroll "Summary" CSV export: one row per employee (occasionally two, when a mid-cutoff rate change splits a row — the second has no No./Name of its own and inherits the last-seen employee), department taken from section-header rows scanned top-down, payroll period from the sheet's title cell. Every value is read at a **fixed column index** (`COL` map); `basic_salary`/`total_earnings`/`total_deductions` are **recomputed from the parts** rather than trusting the sheet's own totals, because the sheet nets the late/undertime deduction into its "BASIC PAY" column while our form (and the printed slip) treats it as a pure deduction line — reusing the sheet's totals as-is would double-count that deduction against NET PAY. Pure, no I/O — unit tested directly. |
| `src/hr-employee-numbering.ts` | `suggestEmployeeNumber(existingNumbers, policy, referenceDate)` — pure (no DB access, same pattern as the two rows above) formatting logic behind the recommended-employee-number feature: scans the given `employee_no` strings for ones matching the policy's `prefix`(+hire-date, in `'hire_date'` mode) and returns one past the highest numeric suffix found, zero-padded to `policy.pad`. Deliberately **derives the next number by scanning current data instead of keeping its own persisted counter** — since `employee_no` is a freely editable/renamable field now, a stored counter could drift arbitrarily far from reality (skipped/renumbered/custom values); scanning is self-correcting by construction and doubles as a peek-only operation (safe to call on every "New Employee" open with no side effect to undo if the user ignores the suggestion). Unit tested directly (`tests/hr-employee-numbering.test.ts`) — sequential continuation with gaps, empty prefix, hire-date per-day suffix reset, YYMMDD vs YYYYMMDD formatting, pad-width overflow. |
| `src/routes/hr.routes.ts` | `/api/hr` — **Employees** master list CRUD (`hr.view`/`hr.manage`): the 201 file — `employee_no` is a **freely editable, required text field**, not server-generated (POST/PUT reject a blank one with 400, and reject a value already used by another employee with 409 — checked with an explicit `SELECT` before the write so the error is a clean JSON message rather than a raw SQLite `UNIQUE` constraint failure), `status` (probationary/regular/resigned/terminated), department/position, statutory numbers (SSS/PhilHealth/Pag-IBIG/TIN), a `photo` data URI, filterable by `department_id`/`status`. **`GET/PUT /hr/employee-number-policy`** (`hr.view`/`hr.manage`, settings key `employee_no_policy`) holds the admin-configurable *format* used only to compute a RECOMMENDATION, never to enforce anything — `EmployeeNumberPolicy {prefix, mode: 'sequential'\|'hire_date', pad, date_format}`. **`GET /hr/employees/suggest-number?start_date=`** calls `src/hr-employee-numbering.ts`'s `suggestEmployeeNumber()` fresh on every request (peeks the current data, mutates nothing — no reserved counter to fall out of sync with reality now that the field is freely editable/renamable) — `'sequential'` mode recommends one past the highest existing `{prefix}-NNNNN` found; `'hire_date'` mode recommends `{prefix}{formatted start_date}-NN`, where `NN` is one past the highest existing suffix already used for that exact date — so a second same-day hire naturally gets `-02` without any separate per-day counter to maintain. Neither mode is enforced: the frontend prefills the suggestion but the field stays a plain editable input, so the company can always type its own number instead (also how numbers survive a switch in `mode`/`prefix` over time — old employees just keep whatever they already have, the recommendation only shapes *new* ones going forward). **Rate is selectable daily or monthly** (`rate_type: 'daily'\|'monthly'`): `daily_rate` is always kept as the *effective* daily rate everyone downstream reads (payroll compute, payslip generation — neither needed any change) — for `rate_type: 'monthly'`, `effectiveDailyRate()` computes and stores `daily_rate = monthly_rate / payroll_policy.monthly_rate_divisor` at create/update time (a stored conversion, not computed live at payslip time, so an employee's `daily_rate` only updates when their record is next saved, not retroactively if the divisor changes later — the divisor rarely changes and this keeps `daily_rate` a single source of truth everywhere else). `employeeSchema` `.refine`s that `monthly_rate` is present and positive when `rate_type === 'monthly'`. **Optionally linked to a login account** (`user_id`, nullable FK → `users(id)` `ON DELETE SET NULL`, enforced 1:1 by a partial `CREATE UNIQUE INDEX ... WHERE user_id IS NOT NULL` since SQLite's `ADD COLUMN` can't carry a `UNIQUE` constraint directly) — ties an employee's 201-file record to the account they log in with. `checkLinkedUser(userId, excludeEmployeeId?)` gives a clean 409 (`"That account is already linked to <name>"`) instead of surfacing the raw index-violation error, and also 409s if the target user id doesn't exist; `excludeEmployeeId` lets an employee keep re-saving its own existing link on PUT without tripping a false self-collision. `GET /employees` LEFT JOINs `users` to also return `linked_username`/`linked_full_name` for display. **`/employees/:id/documents`** — 201-file document uploads (multer `diskStorage`, same shape as `forms.routes.ts`), `hr.view` read / `hr.manage` write. **Time Keeping**: cutoff periods (`attendance_periods`) with a daily time-in/out roster (`attendance_records`, one row per employee per date, pre-populated blank for the period's date range when an employee is added). `GET /periods/:id`'s roster query also returns `department_id`/`status` (not just `department_name`) so the frontend can group/sort by them without a second round-trip. **`POST /periods/:id/employees/bulk`** adds many employees to a cutoff in one call — either an explicit `employee_ids` array (checkbox multi-select in the picker) or a `department_id`/`status`/`q` filter ("Add All", resolved server-side against the `employees` table with the same filter semantics as `GET /hr/employees`, so it always reflects the true matching set rather than whatever page of results the picker happened to have rendered). Idempotent per employee either way (`ensureRosterDays` is `INSERT OR IGNORE`), and the response distinguishes `added` (employees newly put on the roster — computed by diffing against the period's existing `DISTINCT employee_id`s before inserting) from `matched` (total resolved by the filter/id-list), so the UI can report e.g. "added 8 (3 already on it)" instead of a misleading raw count. Each day optionally carries a `shift_id` (which named shift applied — this is how rotating shifts are handled: a day just points at whichever shift ran that day, not a fixed per-employee schedule; `GET/POST/PUT/DELETE /hr/shifts`, `hr.view`/`hr.manage`) and a `form_record_id` (an optional reference to an OT/Half Day/Leave/Undertime/Offset form record for that day, no requirement that one exists). **`GET/PUT /hr/payroll-policy`** (`hr.view`/`hr.manage`, backed by the `settings` key-value store like `company_profile`) holds the company-wide computation *rules* — grace period, late/OT rounding block size, OT rate %, optional night differential, **`monthly_rate_divisor`** (default 26 — the number a monthly-rate employee's `monthly_rate` is divided by to get their effective `daily_rate`) — as opposed to shift *times*, which live in the `shifts` table since those can vary/rotate. `POST /periods/:id/generate-payslips` creates/updates one record per roster employee in the `hr_payroll` form (matched by employee name + period, so re-generating updates rather than duplicates) — now **computes real numbers** via `src/hr-payroll-compute.ts`'s `computeAttendanceForEmployee()` (days worked, late deduction, OT hours/pay, undertime, Holiday Work premiums) from each employee's attendance + whichever forms are linked, resolved into `{shift, linkedForm, noWork}` per day before calling the (DB-free, independently unit-tested) compute function — `noWork` comes from a separate, one-time-per-call lookup against any `no_work_memo` form records (a company-wide declaration, not linked per attendance row — applies to every employee's matching date automatically). Regenerating refreshes every attendance-derived field but preserves purely-manual ones (SSS/PhilHealth/Pag-IBIG/cash advance/rest-day OT/OT peso rate/net pay — no computed source exists for statutory bracket tables) via a `prevManual` carry-over. |

Rows are pre-created blank for the full date range when an employee is added to a cutoff (`ensureRosterDays` in `hr.routes.ts`); hours are entered/edited manually, never auto-computed. |

Foreign keys are ON; deleting a user/department cascades or nulls as defined per column.

## 5. Conventions (follow these to keep the code consistent)

- **DB access:** always go through `queryOne<T>` / `queryAll<T>` / `run` from `src/db.ts`.
  Don't call `db.prepare(...)` directly in routes (the helpers centralize the typed cast).
  Use `db.exec('BEGIN'/'COMMIT'/'ROLLBACK')` only for multi-statement transactions
  (see the inventory `adjust` handler).
- **Validation:** every request body is parsed with `parseBody(schema, req.body)`. Add new
  rules as a schema in `src/validation.ts`, never inline in a route.
- **Types:** shared row/response shapes live in `src/types.ts`. Reuse them; don't redefine.
- **Auth:** routers call `router.use(requireAuth)`; feature-gated handlers add
  `requirePermission('permission.key')` from `src/auth.ts` (preferred over the older
  `requireRole('admin')`). Read the caller via `req.user!`. Frontend checks use
  `App.hasPermission('key')`. The permission list lives in `src/permissions.ts`; the sparse
  per-user overrides are stored in `users.permission_overrides` (JSON) and resolved on every
  request in `userFromToken()`.
- **Errors:** return `res.status(n).json({ error: 'message' })`. Thrown `ValidationError`
  (or anything with a numeric `status`) is shaped by the central handler in `app.ts`.
- **Frontend:** views register with `App.register('name', async (view, filter) => {...})` and
  reuse `API`, `UI.modal`, `UI.toast`, `UI.esc`. Always `UI.esc()` user data before inserting
  HTML. The optional `filter` arg comes from the nav tree leaf (deep-link); honor it via the
  view's existing internal state, never duplicate behavior.
- **Navigation:** the chrome (top primary menu, sub-tabs, left tree, site map, menu search) is
  generated entirely from **`NAV` in `public/js/nav-config.js`** — the single source of truth.
  To add/move a destination, edit `NAV` (a leaf = `{label, icon, route, filter?}`); every
  `route` must be a registered view (`ROUTE_NAMES`, enforced by `tests/frontend-nav.test.ts`).
  Do **not** hand-wire nav buttons in `index.html`. Navigate programmatically via
  `App.navigate(route, filter?)`.
- **Icons:** use `UI.icon('name')` (inline SVG, inherits text color) — do not add emoji or
  icon fonts. Add new glyphs to the `ICONS` map in `ui.js`.
- **Theming:** all colors come from CSS variables defined in `public/css/styles.css` under
  `:root`/`[data-theme='light']` (light) and `[data-theme='dark']` (dark). **Never hard-code
  a hex color in a component** — add or reuse a token (`--surface`, `--text`, `--accent`, …)
  so both themes stay correct. The active theme is the `data-theme` attribute on `<html>`,
  set pre-paint by an inline script in `index.html` and toggled via the right icon rail button.
  Empty tab states use `UI.emptyState(...)`.

## 6. "How to add X" recipes

**A new API endpoint**
1. Add a zod schema in `src/validation.ts` (if it takes a body).
2. Add the handler to the relevant `src/routes/*.routes.ts`, using `queryOne/queryAll/run`.
3. Add the row/response type to `src/types.ts` if new.
4. Add a test in the matching `tests/*.test.ts`.
5. **Add the row to the API catalog (§4) in this file.**

**A new item field (the common case — no DB change)**
1. Add a field def to `ITEM_FORM_DEFAULTS` in `public/js/item-form-config.js` (pick a `tab`,
   `type`, `default`; leave `core` off). It persists automatically into the `attributes` JSON —
   **no migration, schema, or route change.** Admins can show/hide it via the modal's Option panel.
2. To surface it in the table or filters, read `item.attributes.<key>` in `inventory.js`.

**A new *core* item column (only when it needs its own column — e.g. for SQL filtering)**
1. Add the column to `inventory_items` in `src/db.ts` (and an `ALTER` in `migrate()` for old DBs).
2. Extend `createItemSchema` / `updateItemSchema` and the INSERT/UPDATE in `inventory.routes.ts`.
3. Add the field to `InventoryItem` in `src/types.ts` and add `core: true` + the key to
   `ITEM_CORE_KEYS` in `item-form-config.js`.
4. Update §3 here. (`tests/item-form-config.test.ts` enforces core keys ↔ real columns.)

**A new document/template variable**
1. Add the field to the render context built in `printOrder`/`buildContext`
   ([public/js/views/orders.js](public/js/views/orders.js)) and to the editor `SAMPLE`
   ([public/js/views/templates.js](public/js/views/templates.js)).
2. List it in `ORDER_VARIABLES` ([public/js/doc-template.js](public/js/doc-template.js)) so it
   shows in the palette. Templates reference it as `{{group.key}}` (or `{{key}}` inside `{{#items}}`).

**A new frontend view/page**
1. Create `public/js/views/<name>.js` calling `App.register('<name>', (view, filter) => …)`.
2. Add `<name>` to `ROUTE_NAMES` and add a leaf (and primary/subtab if needed) in
   `public/js/nav-config.js` — do **not** hand-add a button to `index.html`.
3. Add a `<script>` tag for the file in `public/index.html`.
4. Update the frontend map in §2. (`tests/frontend-nav.test.ts` will fail if a leaf points
   to an unregistered route.)
