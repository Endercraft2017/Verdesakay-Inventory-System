## 1. Overview

A LAN office system: **inventory**, **forms/files**, **user accounts with roles &
departments**, and **internal messaging**. One PC runs the server; other PCs use it in a
browser.

**Roles & permissions:** 8 roles (`admin`, `admin_staff`, `accounting`, `warehouse`,
`releasing`, `csr`, `hr`, `marketing`) each with granular per-feature permission defaults
defined in `src/permissions.ts`. Admins can override permissions per-individual via the
Accounts UI. Resolved effective permissions are a `Permission[]` on every `AuthUser`.
`forms.manage` (create/edit/delete form definitions + global variables) is admin-only by default.

- **Backend:** Node.js + Express + TypeScript (run with `tsx`, no build step).
- **Database:** SQLite via Node's built-in `node:sqlite` (file: `data.db`).
- **Frontend:** vanilla HTML/CSS/JavaScript SPA in `public/` (no framework, no build step for the
  app itself). One exception: `public/js/vendor/codemirror-bundle.js` — a pre-built CodeMirror 6
  bundle, the project's only external frontend dependency, vendored (not loaded from a CDN, since
  this is a LAN app that may run with no internet access) — see its row in §2 for what it is and
  how to rebuild it.
- **Auth:** bearer session tokens in the `sessions` table (12 h expiry); bcrypt passwords.
- **Validation:** `zod` schemas (`src/validation.ts`). **Security:** `helmet` + login
  rate-limiting. **Tests:** `vitest` + `supertest` (`tests/`).

### Request flow
```
Browser (public/js/*) --fetch--> Express (src/app.ts)
  -> helmet, json/urlencoded, login rate-limit, request log + activity log (mutations)
  -> route (src/routes/*.ts): requireAuth -> requirePermission(key)? -> parseBody(zod)
  -> DB helpers (queryOne/queryAll/run in src/db.ts) -> node:sqlite
  -> JSON response  |  errors -> central handler in app.ts
```

## 2. Directory map (every source file, one line each)

### Backend (`/` and `src/`)
| File | Responsibility |
|---|---|
| `server.ts` | Entry point: `init()` DB, schedule session cleanup, `createApp()`. **Serves HTTPS** (`https` on `PORT`) so the mobile camera/QR scanner works — a self-signed cert is generated on first run via `openssl` into `certs/` (SAN = localhost + every LAN IPv4); a plain-HTTP listener on `PORT+1` 301-redirects to it. If `openssl` is missing it logs a warning and falls back to plain HTTP on `PORT` (scanner then needs manual code entry). Tests never touch this file. |
| `src/app.ts` | **`createApp()`** — builds the Express app: middleware, route mounts, static serving, SPA fallback, central error handler. Imported by both `server.ts` and tests. `helmet` runs with `hsts:false` (so a device can be pointed back at plain HTTP). Request-logging middleware wraps `res.json` (to capture a created record's `id`) and calls `recordActivity` on `finish`. The **`idempotency`** middleware (mounted on `/api`) de-dupes retried mutating requests that carry an `Idempotency-Key` header — no-op without the header. **Device routing**: static assets served with `index:false`, then the fallback auto-redirects phone/tablet User-Agents to the mobile app at `/m` (serves `public/mobile/index.html` for `/m` and `/m/*`); `?view=desktop\|mobile` overrides detection and is remembered in the `vds_view` cookie. |
| `src/idempotency.ts` | **`idempotency(req,res,next)`** — when a `POST`/`PUT`/`PATCH`/`DELETE` carries an `Idempotency-Key` header, the first outcome is stored in `idempotency_keys` and any later request with the same key returns that response verbatim (`Idempotency-Replayed: true`) instead of running the handler. 2xx and deterministic 4xx are stored; 5xx / 401 / 403 / 429 are not (a genuine retry should still run). Keys pruned after 7 days by `cleanupSessions`. Used by the mobile offline queue. |
| `src/clock.ts` / `src/routes/clock.routes.ts` | **Time clock.** Employees prove on-site presence by scanning a QR the office kiosk screen rotates every 60 s — the code is `HMAC(key, floor(epoch/60))` truncated to 10 chars, so it can't be made off-site and a shared screenshot is stale in ~2 min. **No device binding** (a guard at the kiosk hears a distinct chime per punch). `recordPunch()` classifies each punch into a `segment` (`morning_in` / `lunch_out` / `afternoon_in` / `afternoon_out` / …) from the day's punches so far, and de-dupes a repeat within 45 s. `importPunchesForPeriod()` fills `attendance_records.time_in/out` (first/last punch per work_date) for a cutoff's roster, leaving hand-set days alone. `/api/hr/clock` — `GET /code` + `GET /recent` + `POST /kiosk-punch` (`hr.view` — the office PC), `POST /punch` + `GET /my-status` (any user whose account links to an `employees` row), `POST /import/:periodId` (`hr.manage`). Server runs on-site so `new Date()` is office-local. |
| `src/routes/me.routes.ts` | **Employee self-service**, mounted at `/api/me`, everything scoped to the caller's linked `employees` row (403 if unlinked). `GET /me` (the linked employee, incl. `leave_days_remaining` — the mobile Requests view (`public/mobile/views/requests.js`) fetches this to show a "🌴 Leave balance" strip at the top of the list and again on the Leave Request form itself); `GET /me/payslips` (this employee's `hr_payroll` records, matched on `data.employee_name`); `GET /me/schedule` (roster days + shift times for any cutoff not yet ended, `default_shift`); `GET /me/request-types` (the ~12 HR forms an employee may self-file — `REQUEST_SLUGS`); `GET /me/requests` (records this user filed for those forms — `created_by = me`, so no cross-employee leakage); `POST /me/requests/:id/cancel` (withdraw your own still-pending request). Filing goes through the normal `POST /api/form-records` — mobile files with `status: 'pending'`. **Attendance corrections:** `GET`/`POST /me/time-corrections` (file a fix for a missed/wrong punch — `work_date` + `requested_in`/`requested_out` + `reason`; pings the approvers), `POST /me/time-corrections/:id/cancel`. **Approvals inbox** (any hr.manage holder, or the registered head of a department — `departments.head_user_id`): `GET /me/approvals` (`{ requests, time_corrections }` — the caller's decidable pending items, own items excluded), `POST /me/approvals/requests/:id/decide` and `POST /me/approvals/time-corrections/:id/decide` (`{ decision: 'approved'\|'rejected', note? }`). Approving a request flips `form_records.status`; approving a time correction upserts the matching `attendance_records` row (needs a cutoff period covering `work_date`, else `applied: false`). **Approving a `leave_request` with `data.with_pay === 'Yes'` also consumes the filer's fixed leave-day bank** (`employees.leave_days_used += data.days`) — blocked with a 400 if that would push it negative, unless the decision body carries `override_balance: true` (an approver's explicit choice, not the filer's); a rejected decision or an unpaid one never touches it. One-way consumption by design (the "simple fixed bank" — no accrual math, no carry-over); no un-approve path exists to refund it (a wrongly-approved leave is fixed by editing `leave_days_used` directly on the employee). Each decision pushes the filer. `GET /api/auth/me` returns `user.can_approve`. **`GET /me/today`** — the mobile Home "Me" hub: a greeting, the caller's clock state + today's shift + next shift (when linked to an employee), a **ranked `stack`** of actionable items (`{kind, title, subtitle, urgency: high|medium|low, route, count?}` — not-clocked-in, tasks due/overdue, own requests awaiting review, own pending time-corrections, approvals waiting on the caller, unread messages), and the latest active announcement. Works for any logged-in user (HR/clock bits only when linked). |
| `src/routes/announcements.routes.ts` | **Company-wide announcements**, mounted at `/api/announcements`. `GET /` (active/unexpired, pinned first — any user), `GET /all` (incl. expired — `announce`), `POST /` (`announce`; `{ notify: true }` also fires `notifyAll` web-push), `PUT`/`DELETE /:id` (`announce`). `announce` is a default for admin, admin_staff, hr, marketing. ## 3. Data model (SQLite — defined in `src/db.ts` `init()`)

| Table | Key columns | Notes |
|---|---|---|
| `departments` | id, name (unique), **`head_user_id`**→users (SET NULL) | Seeded: Administration, Operations, Finance, Human Resources, IT. `head_user_id` is the user who approves that department's mobile requests / attendance corrections (see `me.routes.ts`); added via `migrate()` ALTER on older DBs. |
| `users` | id, username (unique), full_name, password_hash, role (8 variants), department_id→departments, active, **`permission_overrides` (JSON `{}`)** | 8 roles: `admin`, `admin_staff`, `accounting`, `warehouse`, `releasing`, `csr`, `hr`, `marketing`. `permission_overrides` stores only the sparse diff vs role defaults; resolved by `resolvePermissions()` on every request. Seeded admin on first run. |
| `sessions` | token (PK), user_id→users, expires_at | Bearer tokens; cleaned hourly + on demand. |
| `password_resets` | token_hash (PK, sha256 of the emailed token), user_id→users (CASCADE), expires_at, used, created_at | One-time password-reset links (1 h TTL). A successful reset marks `used` + drops all the user's sessions. Pruned by `cleanupSessions`. |
| `idempotency_keys` | key (PK), user_id, method, path, status_code, response, created_at | Stored outcome of a mutating request that carried an `Idempotency-Key` (mobile offline queue); replayed on a repeat. Pruned after 7 days by `cleanupSessions`. |
| `push_subscriptions` | id, user_id→users, endpoint (unique), p256dh, auth, user_agent | One web-push subscription per browser/device; dead ones are pruned on send (see `src/push.ts`). |
| `time_punches` | id, employee_id→employees, user_id, ts (localtime), work_date, kind (in/out), segment, source (phone/kiosk) | Raw time-clock events; HR reconciles them into `attendance_records` per cutoff (`src/clock.ts`). |
| `time_corrections` | id, employee_id→employees (CASCADE), user_id, work_date, requested_in, requested_out, reason, status (pending/approved/rejected/cancelled), decided_by, decided_at, decision_note | Employee-filed fix for a missed/wrong punch. | `announcements` | id, title, body, pinned, expires_at, created_by→users (SET NULL), created_at | Company-wide notices (`announce` permission to post). `GET /api/announcements` returns unexpired ones, pinned first. |

## 5. Conventions (follow these to keep the code consistent)

- **DB access:** always go through `queryOne<T>` / `queryAll<T>` / `run` from `src/db.ts`.
  Don't call `db.prepare(...)` directly in routes (the helpers centralize the typed cast).
  Use `db.exec('BEGIN'/'COMMIT'/'ROLLBACK')` only for multi-statement transactions
  (see the inventory `adjust` handler).
- **Validation:** every request body is parsed with `parseBody(schema, req.body)`. Add new
  rules as a schema in `src/validation.ts`, never inline in a route.
- **Types:** shared row/response shapes live in `src/types.ts`. Reuse them; don't redefine.
- **Auth:** routers call `router.use(requireAuth)`; feature-gated handlers add
  `requirePermission('permission.key')` from `src/auth.ts` (preferred over the older
  `requireRole('admin')`). Read the caller via `req.user!`. Frontend checks use
  `App.hasPermission('key')`. The permission list lives in `src/permissions.ts`; the sparse
  per-user overrides are stored in `users.permission_overrides` (JSON) and resolved on every
  request in `userFromToken()`.
- **Errors:** return `res.status(n).json({ error: 'message' })`. Thrown `ValidationError`
  (or anything with a numeric `status`) is shaped by the central handler in `app.ts`.
- **Frontend:** views register with `App.register('name', async (view, filter) => {...})` and
  reuse `API`, `UI.modal`, `UI.toast`, `UI.esc`. Always `UI.esc()` user data before inserting
  HTML. The optional `filter` arg comes from the nav tree leaf (deep-link); honor it via the
  view's existing internal state, never duplicate behavior.
- **Navigation:** the chrome (top primary menu, sub-tabs, left tree, site map, menu search) is
  generated entirely from **`NAV` in `public/js/nav-config.js`** — the single source of truth.
  To add/move a destination, edit `NAV` (a leaf = `{label, icon, route, filter?}`); every
  `route` must be a registered view (`ROUTE_NAMES`, enforced by `tests/frontend-nav.test.ts`).
  Do **not** hand-wire nav buttons in `index.html`. Navigate programmatically via
  `App.navigate(route, filter?)`.
- **Icons:** use `UI.icon('name')` (inline SVG, inherits text color) — do not add emoji or
  icon fonts. Add new glyphs to the `ICONS` map in `ui.js`.
- **Theming:** all colors come from CSS variables defined in `public/css/styles.css` under
  `:root`/`[data-theme='light']` (light) and `[data-theme='dark']` (dark). **Never hard-code
  a hex color in a component** — add or reuse a token (`--surface`, `--text`, `--accent`, …)
  so both themes stay correct. The active theme is the `data-theme` attribute on `<html>`,
  set pre-paint by an inline script in `index.html` and toggled via the right icon rail button.
  Empty tab states use `UI.emptyState(...)`.

## 6. "How to add X" recipes

**A new API endpoint**
1. Add a zod schema in `src/validation.ts` (if it takes a body).
2. Add the handler to the relevant `src/routes/*.routes.ts`, using `queryOne/queryAll/run`.
3. Add the row/response type to `src/types.ts` if new.
4. Add a test in the matching `tests/*.test.ts`.
5. **Add the row to the API catalog (§4) in this file.**

**A new item field (the common case — no DB change)**
1. Add a field def to `ITEM_FORM_DEFAULTS` in `public/js/item-form-config.js` (pick a `tab`,
   `type`, `default`; leave `core` off). It persists automatically into the `attributes` JSON —
   **no migration, schema, or route change.** Admins can show/hide it via the modal's Option panel.
2. To surface it in the table or filters, read `item.attributes.<key>` in `inventory.js`.

**A new *core* item column (only when it needs its own column — e.g. for SQL filtering)**
1. Add the column to `inventory_items` in `src/db.ts` (and an `ALTER` in `migrate()` for old DBs).
2. Extend `createItemSchema` / `updateItemSchema` and the INSERT/UPDATE in `inventory.routes.ts`.
3. Add the field to `InventoryItem` in `src/types.ts` and add `core: true` + the key to
   `ITEM_CORE_KEYS` in `item-form-config.js`.
4. Update §3 here. (`tests/item-form-config.test.ts` enforces core keys ↔ real columns.)

**A new document/template variable**
1. Add the field to the render context built in `printOrder`/`buildContext`
   ([public/js/views/orders.js](public/js/views/orders.js)) and to the editor `SAMPLE`
   ([public/js/views/templates.js](public/js/views/templates.js)).
2. List it in `ORDER_VARIABLES` ([public/js/doc-template.js](public/js/doc-template.js)) so it
   shows in the palette. Templates reference it as `{{group.key}}` (or `{{key}}` inside `{{#items}}`).

**A new frontend view/page**
1. Create `public/js/views/<name>.js` calling `App.register('<name>', (view, filter) => …)`.
2. Add `<name>` to `ROUTE_NAMES` and add a leaf (and primary/subtab if needed) in
   `public/js/nav-config.js` — do **not** hand-add a button to `index.html`.
3. Add a `<script>` tag for the file in `public/index.html`.
4. Update the frontend map in §2. (`tests/frontend-nav.test.ts` will fail if a leaf points
   to an unregistered route.)

## 7. Running, testing, building

| Command | What it does |
|---|---|
| `npm start` | Run the server via `tsx server.ts`. **HTTPS on `https://…:3000`** (self-signed cert auto-generated into `certs/` on first run — accept the browser warning once per device; HTTP on `:3001` redirects there). Desktop app at `/`, mobile warehouse app at `/m` (phones auto-redirect). |
| `npm run dev` | Same, with file-watch reload. |
| `npm run typecheck` | `tsc --noEmit` strict type check (no errors allowed). |
| `npm test` | Run the whole Vitest suite once, headless. |
| `npm run test:watch` | Vitest in watch mode. |
| `npm run check` | typecheck **and** test (use before every commit). |

Tests need no setup: each test file creates its own throwaway SQLite DB + uploads dir via
`setupApp()` and removes them after. See `tests/helpers.ts`.

See also **[DECISIONS.md](DECISIONS.md)** for why these tools were chosen.
